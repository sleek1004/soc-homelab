# SOC Home Lab: Reducing Alert Fatigue Through Detection Rule Tuning

A hands-on detection-engineering project: building a Wazuh SIEM lab, measuring false-positive alert noise, and tuning detection rules to cut that noise by **~86%** without losing real threat detection.

---

## The Problem

Every real Security Operations Centre faces the same issue: **too many alerts**. Most are false positives, routine activity that trips a detection rule and generates noise. Over time this causes alert fatigue: analysts become desensitised and start missing the alerts that actually matter.

This project demonstrates the full detection-engineering workflow a SOC analyst uses to fix that: measure the noise, find its source, tune it out safely, and prove the result.

---

## Lab Environment

All virtual machines run natively on Apple Silicon (ARM64) under UTM.

| Role | System | Purpose |
|------|--------|---------|
| SIEM Server | Ubuntu 24.04 + Wazuh 4.14 | Collects and analyses logs, raises alerts |
| Endpoint | Ubuntu 24.04 + Wazuh Agent | Monitored "victim" machine |
| Attacker | Kali Linux | Generates real attack traffic for testing |

---

## Method

### 1. Build
Deployed the Wazuh manager, enrolled an Ubuntu endpoint via the Wazuh agent, and set up a Kali attacker. Along the way I resolved real operational issues: full disks, disconnected agents, and agent/manager key mismatches, the kind of troubleshooting that comes with running a SIEM in practice.

### 2. Measure a baseline
Ran a window of **benign administrative activity only** (SSH login, a sudo command, no attack) and recorded what the SIEM flagged.

> **Result: 14 alerts generated by completely harmless activity.** Every one was a false positive.

### 3. Analyse the noise by rule
Rather than guess, I broke the 14 alerts down by Wazuh rule ID to find the specific culprits:

| Rule ID | Description | Share of noise |
|---------|-------------|----------------|
| 5501 | PAM: session opened | High |
| 5502 | PAM: session closed | High |
| 5715 | sshd: authentication success | Low |
| 5402 | successful sudo to ROOT | Low |

The PAM session rules (5501 / 5502) fire on **every** login and sudo, twice per action, making them the dominant source of fatigue.

### 4. Design and test a tuning rule
I wrote a custom local rule overriding rules 5501 and 5502 to **level 0**, meaning the events are still decoded and logged, but no longer raised as alerts. This is tuning, not deletion: nothing is lost, the noise is simply silenced.

```xml
<rule id="100001" level="0">
  <if_sid>5501</if_sid>
  <description>Tuned: PAM session opened on local benign activity, silenced to reduce alert fatigue</description>
</rule>

<rule id="100011" level="0">
  <if_sid>5502</if_sid>
  <description>Tuned: PAM session closed on local benign activity, silenced to reduce alert fatigue</description>
</rule>
```

Crucially, I validated the rule **offline** with `wazuh-logtest` *before* deploying it, confirming it fired at level 0 against a real PAM log line. Testing before deployment is standard practice: you don't change production detection logic on a hope.

### 5. Deploy and re-measure
After loading the rule and re-running the **identical** benign activity:

> **Result: 2 alerts, down from 14.**

The PAM session noise was gone. The only remaining alerts were the sshd authentication and sudo-to-root events, arguably ones you'd want to keep visible anyway.

---

## Result

| | Alerts from identical benign activity |
|------|------|
| **Before tuning** | 14 |
| **After tuning** | 2 |
| **Reduction** | **~86%** |

Routine session noise was silenced while meaningful security events (authentication, privilege escalation) still surface. Less fatigue, no loss of real detection.
